# iOS AirPlay受信機 統合設計

日付: 2026-09-24
状態: 方針承認済み・本仕様のレビュー待ち。実装・実機互換性は未検証。

## 目的と合意事項

iPhone/iPadをAirPlay受信機にする。画面ミラーリング、その映像と音声の同期、音声専用受信、AirPlay 2の複数受信機同期をすべて開発対象とする。GitHub Actionsで未署名IPAを生成する。App Store公開は予定せず、言語・公開API/非公開APIの制約は設けない。UxPlay、Shairport Sync、NQPTPの移植を組み合わせる方針はユーザー承認済み。

非公開APIを使用してよいという許可は、脱獄済み端末やApple限定entitlementが利用できることを意味しない。初期設計の仮定は、非脱獄端末へ利用者が署名して導入するアプリ。対応開始バージョンはiOS/iPadOS 16、端末アーキテクチャはarm64とする。これらは実装上の初期値で、ユーザー指定ではない。

「すべて」は上記の受信機能を省略しないという要求として扱う。非公開プロトコルの全機能・全送信アプリ・将来のOSとの完全互換が実証済みという意味にはしない。DRM映像、写真送信、HLS動画送信、Homeアプリ登録、AWDL接続、ロスレス/多チャンネル音声も互換性調査表に載せ、未実装・未検証・実機成功・制約ありを区別する。黙って対象から削除しない。

## 採用方式と代替案

採用: SwiftUIのUI、Objective-C++のブリッジ、C/C++の受信コア、iOSネイティブの再生経路。UxPlayから映像受信を、Shairport SyncからAirPlay 2音声受信を移植し、NQPTPの時刻処理をアプリ内に組み込む。

UxPlay単独ではAirPlay 2マルチルーム音声を満たさない。全プロトコルの新規実装は接続互換性と暗号・同期の検証負担が大きいため採用しない。Apple非公開の受信実装を直接利用する方式は、実在するインターフェースと端末上の権限を確認できた場合の代替候補とする。

## 先行して解決する実現性の問題

NQPTPの上流実装はUDP 319/320への排他的アクセスを要求する。上流はmacOSでのポート競合も報告している。iOSについて同じ結果とは断定せず、署名した実機でbind、受信、システムサービスとの競合を検証する。任意のポートへ変更するだけでは送信側互換性を満たしたことにならない。

この検証と、Core Audio出力時刻の取得・PTP時刻への対応付けを最初の技術ゲートにする。成立しなければ、利用可能なシステム時刻同期APIや非公開受信経路を調査する。通常署名で実現できない場合は必要な導入条件を根拠付きで報告し、AirPlay 2対応済みとは表示しない。外部Linuxサーバー必須の構成へ無断で置き換えない。

## コンポーネント

| コンポーネント | 責務・境界 |
| --- | --- |
| ReceiverApp | 受信開始/停止、名前、接続状態、PIN表示、全画面、音量、診断ログ共有 |
| ReceiverCoordinator | サービス識別情報、ペアリング、能力広告、接続と終了の統括 |
| ProtocolAdapter | 上流コードをアプリ内ライブラリとして起動/停止し、所有権が明確なメディア/状態イベントを渡す |
| MirrorCore | UxPlay由来のセッション、復号、映像とミラー音声受信 |
| Audio2Core | Shairport Sync由来のペアリング、realtime/buffered音声、グループ制御 |
| ClockService | PTP/NTP系の時刻を単調増加時計へ対応付け、クロックID・有効期限・不連続を通知 |
| VideoRenderer | H.264と、交渉成立時のHEVCのデコード・表示・PTS処理 |
| AudioRenderer | PCM出力、実出力遅延取得、リサンプリング、ドリフト補正、音量 |

Swift側へ上流の構造体を直接公開しない。C境界は明示的なハンドル、start/stop、設定、イベントコールバックに限定する。暗号化セッションの所有者を接続の途中で入れ替えない。

## 発見・接続の統合

Bonjourの`_airplay._tcp`と`_raop._tcp`を使用する。安定した識別子と鍵を保存し、受信名変更でペアリングが壊れない設計とする。上流の独立した2サーバーを同一IPで起動するだけの方式は採用しない。RTSP/HTTPの初期交渉と認証を調査し、接続を所有するバックエンドとサービスレコードの対応を固定する。

単一受信機として映像・音声の広告が成立するかを送信側で検証する。バックエンドごとのfeaturesビットを単純ORしない。実装済みで動作する能力だけを広告する。必要なプロトコル統合は専用パッチとして管理する。

基本状態は停止、起動中、待受、ペアリング中、受信中、停止処理中、エラー。メディアを再生する送信元は同時に1つとし、別送信元の競合は明示的に拒否する。AirPlay 2のグループ制御接続は同じ再生セッションとして管理する。

## メディア・時刻処理

受信→復号→有界キュー→デコード→送信PTSをローカル時計へ変換→再生、の順とする。映像はVideoToolbox/AVFoundation、音声はCore Audioを使用する。Linux用GStreamer、ALSA、systemd、外部デーモンは実行時依存にしない。上流依存の暗号・plist・デコーダーは必要分をiOS向けに静的リンクする。

音声処理ではサンプル数だけでなく実出力時刻と遅延を追跡する。基準クロック変更、seek、flush、経路変更、接続切断で古いバッファと時刻対応を破棄する。映像の遅れはフレーム破棄で回復し、キュー上限を超えてメモリを増やさない。音声形式は送信側との交渉結果と出力機器能力に合わせる。

音声再生スレッドではネットワーク待ち、ログ出力、メモリ確保を避ける。停止時は広告停止、受信停止、処理スレッド終了、バッファ破棄、再生解放の順に完了を待ち、停止後のコールバックによる解放済みメモリ参照を防ぐ。

## iOS動作と非公開API

ローカルネットワーク許可、Bonjourサービス宣言、音声セッションと割り込み処理を実装する。映像表示は前面を基本とし、音声再生のバックグラウンド継続は実機で確認する。アプリ停止中の常時待受を保証しない。

非公開APIを使う場合は専用アダプターに閉じ込め、OSバージョンとシンボル存在を確認する。必要なentitlement、利用可能な署名方法、失敗時の挙動を記録する。単にentitlementsファイルへ書いた権限を、利用可能とみなさない。

エラーは許可拒否、ポート競合、認証失敗、形式不一致、クロック失効、ネットワーク変更などに分ける。UIには原因と再試行方法を表示する。ログに秘密鍵や復号したメディアを含めない。

## ビルドと配布成果物

GitHub ActionsのmacOSランナーで固定したXcode環境を使用し、上流コミットと依存物バージョン・ハッシュを固定する。アプリと静的依存物をiphoneos/arm64向けにビルドする。署名不要のビルド設定で生成した`.app`を`Payload/Receiver.app`に配置してZIP形式の`.ipa`を作る。署名が必要なexportArchive処理は必須にしない。

成果物には未署名IPA、ビルドログ、採用依存物のコミット一覧、ライセンスと再ビルド手順を含める。IPAのZIP構造、Info.plist、実行ファイルのアーキテクチャとプラットフォーム、欠落した動的ライブラリ参照を検査する。未署名IPAの生成成功と実機へのインストール成功は別々に記録する。利用者による再署名と端末導入の手順を用意する。

上流ソースは変更履歴を追える形で取り込み、著作権表記とライセンスを保持する。移植パッチ、対応するソース、ビルド設定をリポジトリに残す。

## 検証と完了条件

1. 自動検証: malformed RTSP/plist/パケットの拒否、バッファ境界、クロック変換と不連続、flush、停止/再開始の競合を対象にする。上流テストも移植可能な範囲で実行する。
2. CI: クリーンなチェックアウトから依存物と実アプリをコンパイルし、内容検査済み未署名IPAをダウンロードできること。
3. 実機ミラーリング: iPhone/iPad/Mac送信元について接続、映像・音声、回転、切断、再接続、30分連続再生を確認する。映像音声差はテスト映像で計測し、目標100ms以内とする。
4. AirPlay 2: realtime/buffered両経路、ペアリング保持、音量、グループ参加/離脱を確認する。既存AirPlay 2受信機と同じ音源を30分再生し、共通収録による出力差の95パーセンタイル20ms以内を初期合格目標とする。目標は測定結果ではない。
5. 障害: Wi-Fi断、ネットワーク変更、出力経路変更、許可拒否、受信中の停止、前面復帰から復旧できること。
6. 互換性表: 送受信端末、OS、アプリ、コーデック、署名/権限条件、試験日、結果を記録する。追加機能も未確認のまま成功扱いしない。

ビルド環境だけで実機互換性を証明しない。実機を利用できない場合は検証手順と未検証項目を残し、「全機能完成」とはしない。段階的に実装するが、ミラーリングのみで当初要求の完了とはしない。

## 実装順序を決める依存関係

まずビルド基盤と端末でのPTP/音声時刻検証を用意する。次に上流コアのライブラリ化とネイティブ再生を進め、識別情報・認証・能力広告を統合する。最後にグループ同期とライフサイクルを検証する。詳細な作業分割と実行手順は本仕様承認後の実装計画で定める。
